## Platform launch semantics and current code

- Current [Android Debug Bridge documentation](https://www.home-assistant.io/integrations/androidtv/#launching-and-stopping-apps) accepts package app IDs through `media_player.select_source`; `androidtv.adb_command` sends shell/key commands. A foreground activity dump alone does not prove an exported launch entry. The plan should store package identity and optional validated entry separately.
- Current [Android TV Remote documentation](https://www.home-assistant.io/integrations/androidtv_remote/#launching-apps-and-activities) supports `remote.turn_on` with `activity` and `media_player.play_media` for app/URL launching. It warns that package launching fails for many apps after a Google Play Store change, recommending supported deep links when available. Fire TV lacks the required Android TV Remote Service. Android Remote support must be a distinct adapter; it cannot replace Fire ADB globally.
- Current [Apple TV documentation](https://www.home-assistant.io/integrations/apple_tv/#launching-apps) uses `media_player.select_source` for apps and `play_media` for supported content deep links. Exact device-discovered source names are useful launch evidence; App Store numeric IDs and another currently playing app's bundle ID are not equivalent source values. Validate case, Unicode, region, installed version and TV locale.
- Current [Roku documentation](https://www.home-assistant.io/integrations/roku/#source-automation) accepts application name or ID as `select_source.source`. IDs can be obtained from the Active App ID sensor or GET `/query/apps`. The local code currently stores `app-id` but never uses it in dispatch; name changes therefore break launch even when channel ID is unchanged. A future adapter can use an evidenced stable ID and verify type/behavior against the chosen HA version.
- Local [built-in dispatch](https://github.com/Narehood/HomeAssistant-TV-Remote/blob/b856a45e684775fd477dbcd8d1342ff65bb97e38/dist/HA-Firemote.js#L5918) selects an entire family object when it contains any of `adbLaunchCommand`, `appName`, `remoteCommand`; otherwise it selects root fields. It does not merge the root ADB command with a family appName. It sends `remote.send_command` for Apple/Roku remoteCommand, otherwise `media_player.select_source` when no ADB command is defined, otherwise `androidtv.adb_command`. Built-in launchers do not use the associated Android Remote entity, even when navigation does.
- This explains Twitch [#815](https://github.com/PRProd/HA-Firemote/issues/815): its Chromecast family entry selects source `Twitch`; the root Fire-specific ADB command is not inherited. Family editor availability uses [deviceFamily filtering](https://github.com/Narehood/HomeAssistant-TV-Remote/blob/b856a45e684775fd477dbcd8d1342ff65bb97e38/dist/HA-Firemote.js#L8339). Dynamic tuner input exists [outside launcherData](https://github.com/Narehood/HomeAssistant-TV-Remote/blob/b856a45e684775fd477dbcd8d1342ff65bb97e38/dist/HA-Firemote.js#L138). [Custom launchers](https://github.com/Narehood/HomeAssistant-TV-Remote/blob/b856a45e684775fd477dbcd8d1342ff65bb97e38/dist/HA-Firemote.js#L98) already support user actions/scripts and arbitrary labels/icons; keep that escape path.
- Launch source translation is based on [Home Assistant UI language](https://github.com/Narehood/HomeAssistant-TV-Remote/blob/b856a45e684775fd477dbcd8d1342ff65bb97e38/dist/HA-Firemote.js#L5823), not independently discovered TV locale. The German map lacks `Music`/`Photos` source translations despite translated display labels. Separate translated UI labels from protocol/source values and prefer actual available-source aliases.

## Proposed implementation scope and acceptance profiles

These are acceptance requirements for later implementation, not tests performed by this audit. Each matrix row names the applicable profiles and any additional per-app constraint.

- **ANDROID**: identify the installed TV/Fire build, record package and app version/region; launch from home and from another app, both cold and warm; verify target app appears and matching app_id/active state; inspect permission/Activity-not-found failures. Test the actual configured adapter/entity. A supplied Play Store package can be a package-launch candidate, but never synthesize a component from it. Test device/version compatibility before expanding deviceFamily.
- **TVOS**: fetch actual source_list from target Apple TV, use exact case/Unicode/spacing, execute direct HA source selection, then the card; cover relevant TV locale and old/new installed app names. An unrelated active app bundle must not replace the requested source. Deep-link content playback needs separate evidence beyond opening the app.
- **ROKU**: confirm installed channel ID and source name using device/HA discovery, execute direct HA launch then card; retain YAML key across rename, verify old/new display names and ID-based routing if adopted. Do not infer channel ID from the channel-store hash URL.
- **REGRESSION**: capture failing old route and passing new route on a named OS/app version; preserve still-valid legacy/regional builds; test cold/warm starts and active highlighting. Add a focused dispatch/schema test that fails on the actual regression, plus device acceptance. A brand-wide global package replacement is unacceptable without evidence for all affected builds.
- **INTEGRATION**: compare identical direct HA action and card call, inspect target entity and required source data, reproduce configuration/family selection and reload/cache state. For cross-app failures, validate transport first. For custom launchers, test both action/service and script paths without creating duplicate presets.
- **DISCOVER**: resolve product/build/platform identity, obtain source/package/channel ID from official manifest or installed device, and obtain one successful direct launch before shipping. Mark unsupplied platforms blocked rather than filling placeholders.
- **Visual update**: keep launch behavior and saved YAML keys; verify artwork and display alias; do not use translated display text as protocol identity. For Miracast, acceptance additionally includes physical-remote recovery after network control disconnects.
